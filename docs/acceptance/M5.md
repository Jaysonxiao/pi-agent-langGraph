## A. 从面出发：范围与系统位置

M1–M4 提供工程、最小模型图、fake 工具循环和安全工具/文件审批组件。M5 把运行中的框架输出转换为稳定事件，再通过 CLI 提供 JSONL 或文本。M6 将在状态图处接入持久 checkpoint 与 session 元数据。

- **目标**：让 Agent 运行过程可观察，并形成流式 CLI。
- **确定范围**：同步 stream 的 token/state/tool/custom 适配、JSONL DTO、简单 CLI、Ctrl+C 协作取消、fake 演示。
- **实际交付范围**：三模式同步投影、text/JSONL、fake 最小图 CLI、消费侧 token、临时 SIGINT handler、首终态截止和明确退出码。
- **非目标**：完整 Pi TUI、图片、远程 RPC；真实 provider 和生产级供应商运行时按 M8 推进。
- **交付物**：events 包、cli 包、pi-agent console script、对应单测与集成测试。
- **验收标准**：token 与工具进度按顺序输出；最终状态只发布一次；取消不继续消费并释放已启动的迭代器资源。
- **验证命令**：见 C 节；命令基于当前仓库，不把未来入口写成已实现。

贯穿请求及真实接线：

```text
pi-agent --provider fake --prompt hello --events text|jsonl
  → argparse / create_initial_state
  → build_minimal_graph + RunContext(FakeChatModel)
  → graph.stream(["updates", "messages", "custom"])
  → project_stream_chunks
  → iter_cancellable(token)
  → iter_terminal_once
  → render_event / iter_jsonl
  → output.write + output.flush

sigint_cancels(token) 包围消费循环：
  进入保存并安装 handler → SIGINT 设置 token → 退出恢复旧 handler
```

默认 `hello` 输出依次为 assistant 的 fake reply 与 completed 状态。无密钥脚本流通过同一 `run_cli()` 管道验证 message token、tool、custom progress 与 terminal 的顺序。CLI 仍使用最小模型图，不代表已经接入 M3/M4 的真实工具能力。

## B. 进入点：Pi 映射、模块和契约

沿用项目固定 Pi 快照的设计理解：`packages/agent/src/agent-loop.ts` 负责模型/工具循环及事件发布，`packages/coding-agent/src/core/agent-session.ts` 在外层协调会话与消费者。本项目保留“核心运行与展示解耦”的原则，改用 LangGraph chunks 投影到自有 DTO；未照搬 Pi 的完整事件或 TUI 协议。本次未重新拉取或复核上游源码。

| 层 | 代码 | 职责与边界 |
|---|---|---|
| 单事件投影 | events/stream.py、message.py、custom.py | 分类、JSON 字段筛选、role/chunk、progress 校验 |
| 模式适配 | events/adapter.py | 拆分三种 mode；按实际产出分配 sequence |
| 序列化 | events/jsonl.py | 惰性紧凑 JSON；一事件一行 |
| 可读展示 | cli/render.py | 纯函数，不直接执行 IO |
| 取消请求 | cli/signals.py、cancel.py | 保存/恢复 SIGINT handler，token 和迭代控制 |
| 终态过滤 | events/terminal.py | completed/failed/error 为首终态；发布后立即关闭上游 |
| CLI 组装 | cli/app.py | fake 最小图、三模式事件管道、逐事件 flush、0/1/130 退出码 |

sequence 在投影阶段连续分配；终态是最后发布的事件，过滤器随后关闭上游，不再触发后续事件或副作用。若上游在终态前自行丢弃事件，sequence 仍以投影结果为准，不在展示层重编号。

### M5-R1–R4 闭合记录

- **M5-R1 已闭合**：删除“为触发 finally 先 next”的行为，统一使用 `close_iterator()`。测试使用可跟踪 iterator，明确断言预取消时 `next_calls == 0`、`close_calls == 1`。
- **M5-R2 已闭合**：adapter、terminal、renderer、JSONL 和 CLI 都在 `finally` 中传播关闭；CLI 作为 graph stream 所有者再次兜底关闭 raw stream。集成测试直接跟踪 raw close，另覆盖 output.write 异常。
- **M5-R3 已闭合**：error 与 failed/completed 都进入统一终态判定；首终态发布后截止；CLI 对成功、失败、取消分别返回 0、1、130，缺少成功终态也按失败处理。
- **M5-R4 已闭合**：CLI 请求 updates/messages/custom 三模式；无密钥脚本流通过真实 `run_cli()` 验证 token/tool/progress/terminal 顺序；每次 write 后显式 flush。默认 fake minimal graph 不产生工具调用，这是演示输入能力边界，不是事件消费缺口。

### 学习复盘与下一阶段接口

M5 之前调用方需要理解框架的原始消息和状态更新；现在有了可测试的 event→JSONL/text→CLI 边界。LangGraph 提供执行与 chunk，应用仍须定义资源所有权、终态、取消和输出时机。完成一个小函数与完成一项系统验收之间，仍需要真实跨层证据。

1. 为什么预取消时不要求未启动 generator 的 finally 执行？答：其主体和资源获取都尚未发生；强制 next 反而制造副作用。需要验证的是不启动生产者，并对显式 closeable owner 调用 close。
2. 为什么关闭要逐层传播？答：CLI 只持有包装后的 iterator；每层 `finally` 都必须把 teardown 传给自己拥有的上游，最终到达 raw graph stream。
3. 为什么首终态后直接停止？答：completed/failed/error 已定义一次运行的边界，继续消费会让“最终事件”失去语义，并可能触发不应发生的上游副作用。

M6 将从 graph state/checkpointer/session metadata 处接入，不从 renderer 或 JSONL 文本反推会话。本次未开始 M6。M5 的同步流式边界已经闭合；真实 provider/tool 的异步取消、超时和任务中断继续由 M8 负责。
