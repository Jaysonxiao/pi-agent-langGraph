## A. 从整体看本阶段

```text
M1-M6 completed                                                        M7+ pending
输入 -> Agent 图/工具/事件 -> session_id/thread_id -> checkpoint + metadata -> 恢复/历史/fork
                                      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                                    M6 负责
```

M5 的 CLI 每次启动都创建一张无持久化的最小图，因此进程退出后对话状态消失。M6 要让运行状态有稳定会话身份并可恢复，同时保持三个边界：模型和工具仍由 `RunContext` 注入而不写入 checkpoint；checkpoint 保存 thread 内图状态；session metadata 保存名称、创建时间等应用数据。

完整 M6 的目标、范围、非目标、交付物、验收标准和验证命令以 [PLAN](../../PLAN.md) 为准。归档只覆盖开发用 SQLite 与当前应用接口，不等同生产级多租户持久化。

## B. 端到端验收场景

贯穿场景：

```text
进程 A
  session-1 + "remember alpha" + user-1
    -> session_config(thread_id=session-1)
    -> graph.invoke(AgentTurnInput, durability="sync")
    -> SQLite checkpoints: [Human(user-1), AI(assistant-1)]
  -> 关闭连接/进程

进程 B
  重新打开同一个 SQLite 文件
  session-1 + "what should you remember?" + user-2
    -> get_state(session-1)
    -> 若 snapshot.next 非空，拒绝普通新一轮
    -> graph.invoke(新 AgentTurnInput, 同一 thread_id)
    -> add_messages 合并旧历史和新消息
    -> 模型看到 Human1, AI1, Human2
```

失败路径也属于契约：空白消息必须在调用模型前失败；不同 `thread_id` 不共享消息；暂停在待执行节点的 checkpoint 不能被普通用户输入越过。这三条路径均已通过直接测试。

## C. 设计来源与改写选择

问题是“进程重建后如何继续同一会话”，不是“如何把 Python 对象缓存起来”。Pi 的 coding-agent 在 Agent 核心循环外由 SessionManager/AgentSession 协调会话记录；本项目把这一分层映射为 `sessions/` 应用层与 LangGraph checkpointer。

LangGraph 的当前契约是：checkpointer 在 super-step 边界保存状态，`thread_id` 是读取和写入 checkpoint 的身份；同一 thread 的后续消息作为一次新的 graph input 进入 reducer。`Command(resume=...)` 专门恢复 `interrupt()`，不能替代普通多轮输入。SQLite saver 是本地轻量同步实现，生产存储不会绑定到本模块。

| 问题 | 改写选择 | 代码位置 | 当前证据 |
|---|---|---|---|
| 图此前不能注入 saver | builder 接收可选 `BaseCheckpointSaver` | `graph/builder.py` | 原有无 saver 调用保持兼容；SQLite 单轮 smoke 通过 |
| 完整 state 与本轮输入混淆 | 增加 `AgentTurnInput`，由 state reducer 合并 | `domain/state.py` | 原 M2/M3 测试接口不变 |
| session ID 漂移 | 集中映射并拒绝空白、首尾空格和超长 ID | `sessions/config.py` | 6 项配置测试通过 |
| SQLite 连接泄漏 | context manager 集中打开/关闭 | `sessions/sqlite.py` | 文件落盘和目录误用测试通过 |
| 普通续聊与 interrupt resume 混淆 | 应用层 `run_session_turn()` 管理新一轮 | `sessions/runtime.py` | 4 项原红灯均已转绿 |
| 历史泄漏框架对象 | 投影为不可变 `SessionCheckpoint` | `sessions/history.py` | newest-first、严格字段校验通过 |
| fork 重放节点或污染 source | `update_state()` 写独立 target，不调用 `invoke()` | `sessions/fork.py` | source 隔离且 fork 期间模型调用不增加 |
| checkpoint 与应用目录混合 | 独立 `pi_agent_sessions` metadata 表 | `sessions/metadata.py` | UPSERT、UTC、重开与并行写通过 |
| 损坏 SQLite 泄漏底层错误 | `SessionCheckpointError` 保留异常链 | `sessions/sqlite.py` | 无效数据库文件回归通过 |
| CLI 误入 Agent 执行 | 独立 `session list` 路由 | `cli/app.py` | 稳定 JSONL 且不构图 |

## F. M6.2 — checkpoint 历史投影

M6.1 能恢复“最新状态”，但 CLI 和 fork 不能依赖 LangGraph `StateSnapshot` 的完整内部结构。M6.2 增加稳定 `SessionCheckpoint`，并保持 `get_state_history()` 的 newest-first 顺序：

```text
SQLite thread checkpoints
  -> graph.get_state_history(session_config)
  -> StateSnapshot（框架类型）
  -> project_session_checkpoint
  -> SessionCheckpoint（应用 DTO）
  -> session history consumers / checkpoint fork
```

唯一学习任务：

- 目标文件：`src/pi_agent/sessions/history.py`
- 目标签名：`project_session_checkpoint(snapshot: StateSnapshot) -> SessionCheckpoint`
- 必须提取：`config.configurable.checkpoint_id`、`created_at`、`metadata.source`、`metadata.step`、`values.status`、`len(values.messages)`、`snapshot.next`。
- 校验：checkpoint ID、时间和 source 必须为非空字符串；step 必须是精确 `int` 且拒绝 `bool`；status 只能是既有 `RunStatus` 或 `None`；values/messages/config/metadata 形状错误必须抛出指出字段的 `ValueError`。
- 输出：构造新的不可变 `SessionCheckpoint`；`next_nodes=tuple(snapshot.next)`。
- 约束：不得保存或返回原始 snapshot/messages；不得使用 `str()` 掩盖错误类型；不得排序历史；不得读取 SQLite 或调用 graph。
- 测试：`tests/sessions/test_history.py`、`tests/integration/test_session_history.py`。
- 完成验证：学习者报告目标范围 `3 passed`、组合范围 `15 passed`，目标 mypy 10 个文件与 Ruff lint/format 通过。实现严格校验 DTO 字段，并未保留原始 snapshot/messages。
- 完成标准：跨连接历史 newest-first，最新摘要为 `completed`、4 条消息、无待执行节点；checkpoint ID 唯一；不存在的 session 返回空列表。

## G. M6.3 — 从已完成 checkpoint 分支

完整线程复制与状态分支不是同一件事。当前 `BaseCheckpointSaver.copy_thread()` 的官方契约要求复制完整祖先链和 writes，但锁定的 `SqliteSaver 3.1.1` 没有实现该方法。本切片用公开图 API 建立“从选中状态开始的新 thread”：

```text
source_session + checkpoint_id
  -> graph.get_state(source checkpoint)
  -> 要求 status=completed 且 next=()
  -> 要求 target thread 尚不存在
  -> graph.update_state(target, source.values, as_node="model")
  -> target 独立 checkpoint（不执行节点）
  -> target 后续 run_session_turn 独立续聊
```

唯一学习任务：

- 目标文件：`src/pi_agent/sessions/fork.py`
- 目标签名：`fork_session(graph, *, source_session_id, checkpoint_id, target_session_id) -> SessionCheckpoint`
- 身份：调用 `checkpoint_config()` 与 `session_config()`；source 和 target 相同必须抛出 `SessionForkError`。
- target 门禁：先 `graph.get_state(target_config)`；只要 `created_at is not None` 就视为已占用并拒绝，不能用 state truthiness 猜测。
- source 门禁：按指定 checkpoint 读取 snapshot；缺失 checkpoint、`next` 非空或投影后 `status != "completed"` 均抛出包含相关 ID 的 `SessionForkError`。
- 分支：调用 `graph.update_state(target_config, snapshot.values, as_node="model")`；不得调用 `invoke()`，不得手工拼接 messages。
- 返回：用 update_state 返回的 config 重新 `get_state()`，复用 `project_session_checkpoint()` 返回稳定 DTO。
- 约束：不得修改 source；不得覆盖 target；不得直接写 SQLite 表；不得调用未实现的 saver `copy_thread()`；不得声称复制了 source 完整历史。
- 完成验证：学习者修复 pending-node 门禁后报告 fork 目标范围 `4 passed`、组合范围 `24 passed`。source/target 身份、目标占用、缺失 checkpoint、source 隔离和 pending-node 拒绝均有覆盖；此前 mypy 12 个文件与 Ruff lint/format 通过。
- 完成标准：从 source 第一轮 checkpoint 分支后，source 保持两轮 4 条消息，branch 从第一轮 2 条消息继续并独立达到 4 条；已存在 target 与缺失 checkpoint 明确失败。

## H. M6.4 — 应用 session metadata

checkpoint 的存在不能代替应用会话目录：列表、创建/更新时间、后续标题与 parent 分支信息都应由应用表管理，不能把第三方 saver 的内部表当作本项目 schema。

```text
SqliteSessionCatalog(database_path)
  -> pi_agent_schema_migrations（本项目 schema 版本）
  -> pi_agent_sessions（session_id, created_at, updated_at）
  -> CLI `session list` / fork parent metadata
```

唯一学习任务：

- 目标文件：`src/pi_agent/sessions/metadata.py`
- 目标签名：`SqliteSessionCatalog.record_session(session_id: str) -> SessionRecord`
- 输入：受 `session_config()` 相同规则约束的 session ID；catalog 构造时的 injectable clock 只用于可重复测试。
- 实现：先以 `session_config(session_id)` 验证 ID；在一次 SQLite connection context 中运行 `_migrate()`；用一条 `INSERT ... ON CONFLICT(session_id) DO UPDATE` 完成创建或 touch；随后读回并返回准确 `SessionRecord`。
- 时间：调用 `self._clock()`，转换为 UTC ISO-8601；同一 ID 的 UPSERT 绝不能覆盖 `created_at`，只能更新 `updated_at`。
- 约束：不得读取或修改 LangGraph 的 checkpoint/writes 表；不得创建第二套 schema 版本表；不得用先 SELECT 再 INSERT/UPDATE 的两步模拟 UPSERT；异常不得吞掉。
- 完成验证：学习者修复 UTC 规范化和 naive clock 拒绝后报告 `5 passed`；助手复跑同一 metadata 范围为 `5 passed`，mypy 11 个文件、Ruff lint/format 通过。可选 `SessionCatalog` 接线另有 2 项测试：终态图运行后记录 metadata，暂停 thread 被拒绝时不记录。
- 完成标准：migration 仅记录一次；同一 session touch 保留创建时间；重新创建 catalog 后仍可列出该 session。

## I. M6.5 — metadata migration 恢复与并行写入

M6.4 的 migration 有两个动作：确保 `pi_agent_sessions` 表存在，再写入 schema marker。进程可能恰好在这两步之间退出；重新启动时，应用不能把已有表误判为 migration 冲突。

```text
第一次启动：创建 sessions table ──[进程退出]──> marker 缺失
下一次启动：重复 migration → 表保持存在 → marker 补齐 → catalog 可用

两个独立 catalog：各自 connection → 幂等 migration → SQLite UPSERT → 两条 session metadata
```

唯一学习任务：

- 目标文件：`src/pi_agent/sessions/metadata.py`
- 目标方法：`SqliteSessionCatalog._migrate(connection)`。
- 要求：所有 DDL 都必须幂等；schema marker 的插入必须能安全重试；marker 只能在 sessions 表已经可用后写入。
- 约束：不得删除现有 metadata；不得重建或读写 LangGraph checkpoint/writes 表；不得把并发异常静默吞掉；保留 `METADATA_SCHEMA_VERSION` 作为唯一 schema 标识。
- 测试：`tests/sessions/test_metadata_recovery.py`。
- 实现：`pi_agent_sessions` 使用 `CREATE TABLE IF NOT EXISTS`；在表可用后以 `INSERT OR IGNORE` 写入 marker，避免恢复或并行启动时重复插入版本记录。
- 完成标准：中间态数据库可恢复且 marker 恰好一条；并行写入后两个 ID 都可列出。

## J. M6.6 — 损坏 checkpoint 存储错误边界

`SqliteSaver` 在 context manager 打开后仍会延迟到 `get_state()`/`invoke()` 才执行建表或读取，因此异常转换覆盖 `yield` 的整个使用期。无效数据库文件产生的 `sqlite3.DatabaseError` 被转换为带绝对路径的 `SessionCheckpointError`，并通过 `raise ... from error` 保留根因；`OperationalError` 原样抛出，锁冲突不会被误报为数据损坏。
