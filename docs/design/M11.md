## B. 进入点

### 同一个请求的数据流

1. `run_tool_case(case)` 创建独立 TemporaryDirectory，其中 workspace 只含合成 `probe.txt`，数据库位于 workspace 外。
2. fake 模型第一轮返回 list/read 两个调用；async tools 顺序校验并执行实际文件操作。
3. 每个调用产生 before_tool/after_tool；结果作为 ToolMessage 回到第二轮模型。
4. fake 模型检查结果顺序和成功状态，再从 read 返回值生成回答。期望答案不参与执行。
5. `stream_provider_session()` 消费到结束；外层 aclosing 确保异常时也关闭。run_end 和 model/tool hooks 一起保留在内存。
6. `collect_tool_names(events)` 把成功的工具完成事实转换为有序 tuple。
7. `EvalHarness` 比较实际回复和工具轨迹；仅输出 case ID、布尔 checks 和计数。临时文件、SQLite 与正文不作为报告交付。

如果工具失败，after_tool 的 outcome 为 failed；fake 模型拒绝把错误结果当摘要，运行器记录失败，executor 拒绝正常 verdict。若 TODO 未完成，公开 CLI 返回 1 并仅报告 `NotImplementedError` 类型；这是未通过，不能当成功 smoke。

### 问题 → Pi 设计 → Python 选择 → 证据

上游基线仍是 `earendil-works/pi@96317e50b8d6e7f6d0e47fd29122baf1461c00f5`。本轮实际读取了固定提交的 [agent-loop.ts](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/agent/src/agent-loop.ts)。server/client 的固定提交页面本轮读取失败，不把缓存失败替换成 main 基线；远程源码映射沿用 [M10 已核对记录](M10.md)。

|---|---|---|---|
| 模型调用后如何继续 | `runLoop()` 调 `streamAssistantResponse()`，把工具结果加入消息后继续 | `build_async_tool_graph()` 用 model/tools 与条件边表达控制流 | `graph/builder.py`、`graph/async_nodes.py`；现有 graph/integration 测试 |

| 持久化能否替代外部资源管理 | 此处不从 Pi 循环推断数据库或连接保证 | checkpointer 保存 thread 状态；应用负责连接、task、文件和审批 | `sessions/async_runtime.py` 与 M8/M10 验收 |

[LangGraph persistence 官方文档](https://docs.langchain.com/oss/python/langgraph/persistence) 区分 thread 范围 checkpointer 与跨 thread store。本项目没有借框架之名宣称外部副作用恰好一次。源码与当前依赖接口核对无变更需求，未升级库。

需要掌握的知识按数据流排列：模型请求只是意图；工具结果是执行事实；reducer 合并消息而非 telemetry；hook 提供运行期观察；身份决定去重范围；judge 必须比较独立期望与实际输出。sequence 只在一次 run 中递增，不是跨 run 的全局时钟。

### 唯一学习者练习

目标：[tool_trace.py](../../src/pi_agent/evals/tool_trace.py)。只填这个函数：

```python
def collect_tool_names(events: Sequence[HookEvent]) -> tuple[str, ...]: ...
```

输入是已经通过 HookEvent 校验、按到达顺序排列的事件，可包含多个 thread/run。输出是成功完成工具的名字 tuple。要求：

- 只接收 `phase == "after_tool"` 且 `outcome == "completed"` 的事件。
- 以 `(thread_id, run_id, tool_call_id)` 作为去重键；同一个完成事件重复出现只计一次。
- 不按工具名去重；不同 call 的两次 read 必须保留两次。
- 保持输入中的首次有效到达顺序，不按 sequence 排序；不同 run 的 sequence 可从零开始。
- 空输入、只有 before/失败/取消事件时返回空 tuple；不修改输入、不执行 I/O、不捕获并吞掉 TODO。
- HookEvent 保证工具事件有 name 和 call ID；类型检查仍需合理缩窄 Optional 字段。

例子：`before(read,A) → after(read,A,completed) → 重复 after(read,A) → after(read,B,completed)` 应得到 `("read", "read")`。A/B 的完整身份包括 thread 和 run。

先运行聚焦验证，再运行集成：

```powershell

uv run pytest tests/evals -q --basetemp=.pytest-tmp-m111
uv run pi-agent eval --suite smoke --provider fake
uv run pi-agent eval --suite tools --provider fake
uv run mypy src tests
uv run ruff check .
uv run ruff format --check .
```

初始脚手架曾保留 TODO，预期 eval 为 5 passed / 6 failed；这是已解决的教学停点，不是当前状态。学习者完成后，聚焦 eval 为 11 passed，smoke/tools CLI suite 各 1/1。

## C. 从点回到面（审查时完成）

M11.1 已完成：学习者的投影将 `after_tool(list/read)` 变成 `(list, read)`，公开 tools suite 为 1/1。回到整体后，M11.2 又把同一 async runtime 的 lifecycle 接到 compatible CLI opt-in sink；真实临时 read 在 telemetry file 中只留下 `tool_name=read`、call/run identities 和 completed outcome，不记录 probe 正文、prompt 或 API key。文件变更位于 `cli/telemetry.py`、`telemetry/jsonl.py` 和 `cli/app.py`，由新的 sink/CLI 测试覆盖；默认 fake 路径不创建 telemetry 文件。

M11.1/M11.2 闭合 M9 登记的 fake 工具 eval 和默认 CLI 无 lifecycle telemetry 的缺口；它们不证明真实模型会正确选工具、真实后端互通或跨资源恰好一次。去重只过滤观察列表中的重复通知，不阻止实际工具执行重复。M11.3 的 Windows 本地 smoke、loopback fake 性能样本与 SQLite resource warning 修复已完成；全量 warnings-as-errors 测试 579 passed、4 个 live tests skipped。Windows/Ubuntu CI matrix 配置已加入，但新环境 jobs 的实测结果仍未取得。M11.4 已汇总 threat model、验收矩阵和分析清单，见架构复盘。
