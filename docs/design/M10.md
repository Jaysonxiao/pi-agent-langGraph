## A. 从面出发：让另一个进程使用现有 Agent

已交付的本地请求从 CLI 进入上下文装配、模型/工具循环，再把会话写入 SQLite；M9 增加观察 hook、telemetry 和离线 eval。另一个进程还不能通过明确的协议提交请求、查询执行状态，也无法知道断线前的请求是否完成。M10 在图外补齐这一段。

```text
已有本地入口 CLI ───────────────────────────┐
                                           v
新增客户端 → 有界传输/认证 → 协议握手/派发 → 会话运行边界
                  [M10]                        |
                              上下文 → model → tools → model
                                 [M7]   [M8]    [M3/M4]
                                               |
                                      checkpoint / SQLite [M6]
                                               |
客户端 ← 请求响应 / 进展事件 / 权威快照 ← 安全投影 [M10]

已有 hooks / telemetry [M9] 观察同一 thread/run/model/tool
后续 M11：全链路验收与最终架构复盘
```

贯穿请求固定为：**客户端请服务端读取服务端工作区中的 `probe.txt` 并总结**。在临时工作区放入合成文本，由可控 fake 模型产生真实 read 调用，再根据 ToolMessage 返回确定回复。fake 普通回复 smoke 和这个工具调用场景分别验证，不能用 echo 成功代替工具闭环。

1. 服务端启动时确定 workspace、database、model 工厂和认证配置；客户端提供 prompt，不提交这些服务端配置。
2. 客户端通过认证与版本握手，调用 `create_session`，取得服务端生成的 session ID `S`。
3. 客户端以 request ID `R1` 向 `S` 提交 prompt；服务端领取运行 `U1`，派发可关联的开始/进展事件。
4. 公共运行器使用 `S → thread_id`、新 message ID 和同一个 `U1 → run_id` 进入已有 async tool graph；read 结果成为 ToolMessage，下一次模型调用生成回复。
5. 服务端等待图运行与持久化结束，生成快照；客户端按 `R1` 完成对应等待，展示服务端给出的结果。
6. 客户端重新连接并调用 `get_snapshot(S)`，取得权威状态；普通续聊从 SQLite 的最新完整 checkpoint 继续。

失败场景也沿这条链：长度超限在解帧时停止；未认证在业务前停止；第二个同会话 prompt 返回 busy；断线使客户端结果变为未知，服务端取消该连接拥有的运行并清理；重连只查询快照，不能自动重发 prompt。若取消留下未完成 checkpoint，返回 `needs_recovery`，本阶段不自动恢复或重放工具。

## C. 首版契约与边界

下面是本次规划确定的默认方案；切片实现发现证据冲突时先修订对应决定和验收断言，不能默默扩张功能。

| 边界 | M10 决定 |
|---|---|
| 部署与信任 | 单进程服务，单信任主体。服务端只绑定 `127.0.0.1`，客户端同样只连本机；测试端口为 0，由 OS 分配。跨机器接入/TLS/公网部署属于后续能力 |
| 配置归属 | workspace/database/provider 由服务端启动参数确定；默认 fake，compatible 显式启用。数据库放在工具 workspace 外，避免 read/list/search 暴露 checkpoint；拒绝违反此边界的服务端配置 |
| 认证 | 服务端和客户端从 `PI_AGENT_REMOTE_TOKEN` 环境变量读取 token，缺失即失败。认证前导独立于业务 hello，最多 4 KiB、5 秒；常量时间比较；失败关闭连接并不返回任何 session 内容。token 不写入请求 DTO、checkpoint、日志或错误 |
| 协议 v1 | 四字节 unsigned big-endian 长度 + UTF-8 JSON；默认 max frame 1 MiB；入站/出站都检查；零长度拒绝。JSON 拒绝重复 key、NaN/Infinity 与额外字段。长度只限制 wire 大小，仍需限制嵌套/字段及消息数量 |
| 连接阶段 | `authenticating → awaiting_hello → ready → closing → closed`；认证完成后才构造业务 connection；hello version 必须是严格整数，未知版本返回固定安全错误后关闭 |
| 命令 | `create_session` 无路径/模型参数；`get_snapshot(session_id)`；`prompt(session_id, text)`；`cancel(session_id, run_id)`。未知 session 不隐式创建；首次 create 返回的 ID 必须先持久登记再报告成功，重启后空会话仍可查询 |
| 标识 | request ID 是连接内单调递增的严格正整数，上限 `2**63-1`；session ID 由服务端生成并映射到 thread_id；message ID 每轮新建；run ID 同时用于远程事件和 M9 hook；server epoch 每次启动新建，connection epoch 每次连接新建 |
| 请求重复 | 请求 ID 是关联标识，不是持久幂等键。同连接用单调递增序号拒绝已用 ID，避免无界保存全部历史 ID；重连不重发未知 prompt，不声称跨重启 exactly-once |
| 执行响应 | prompt 可先发 `run_started` 事件（包含 run_id），最终只发一个对应 request 的 response。`ok=true` 表示命令完成处理，图 outcome 仍可为 failed/cancelled；协议/门禁失败则 `ok=false`。事件流中不再另造一个与 response 竞争的最终成功信号 |
| 状态权威 | snapshot 包含 session_id、server_epoch、revision、checkpoint_id、graph_status、run phase/outcome、active_run_id、message_count 和有界展示消息。运行 phase 与 graph status 分开；快照从已提交 checkpoint 和服务端运行记录生成，不从客户端进展消息反推 |
| 一致读取 | session 协调器保护快照缓存和 revision 的原子替换；只有 durable 节点更新/运行状态切换才更新快照。查询取最近已发布的一致快照；最终 response 前刷新最新 checkpoint。不能在一次 await 前后混合旧 revision 与新正文 |
| 展示上限 | 最近最多 20 条消息，单条文本最多 8 KiB，整体展示最多 128 KiB，按 UTF-8 边界截断并显式返回 `truncated` 与总消息数。只发角色、ID、展示文本、必要 tool call 关联，不发 system prompt、原始 metadata、任意 tool args 或数据库路径；wire 编码仍执行 1 MiB 上限 |
| 资源预算 | 最多 16 条连接、全局 4 个活动 run、每连接 8 个在途请求；pending 输出总量最多 2 MiB，发送/关闭有 deadline。上限可由服务端受控配置降低；慢消费者断开并清理，不能用无限 queue 消化 |
| 并发 | 同 session 仅一个运行，第二个 prompt 立即 busy；不同 session 可在全局上限内并发。长运行与 socket 接收分 task，避免 cancel 被 prompt 阻塞。cancel 必须匹配当前 run_id，防止迟到取消杀掉下一轮 |
| 断线与超时 | 服务端取消该连接拥有的活动 run 并 await 清理；仍在清理时 session 保持 busy，清理超时转 needs_recovery。客户端 pending 全部失败且旧快照 stale；请求 timeout 关闭连接并报告执行结果未知，重连后先查询 |
| 重启与恢复 | 完成的 checkpoint 可续聊；没有运行记录却存在 pending `next`/不完整状态时标记 needs_recovery 并拒绝新 prompt，不自动执行旧工具。重启产生新 epoch，revision 可从 0 开始；不得与旧 epoch 数字比较 |
| 运行依赖 | 模型与 saver 的创建/关闭有明确 owner；每会话/运行使用可隔离的 fake 状态与唯一消息 ID。共享的 provider 资源如需复用，必须有显式并发/关闭合约，不能借复用之名共享可变 fake reply 队列 |
| 安全与观察 | 只读 registry；认证凭据与 provider 凭据分开；远程日志只记录关联标识、状态/错误码与计数。网络向已认证用户返回合约允许的正文，telemetry 不记录正文；验证异常只能映射为安全错误，不序列化其 input |

采用独立认证前导后，接收器必须保留同一次 read 中认证之后的字节，交给 hello parser；测试要覆盖 auth、hello、业务帧连在一起到达。协议 request 在客户端握手完成前不发送；服务端仅接受 ready 阶段业务消息。单 reader 负责读取，发送通过一个有界串行 writer，避免并发结果穿插破坏 framing。

服务端会话新建可复用 metadata catalog 登记空 session；checkpoint 首轮生成。查询以 checkpoint 为执行事实，metadata 只表示会话存在，不能以 updated_at 推断运行成功。checkpoint/catalog 仍是独立写入，不在 M10 宣称已解决跨连接原子事务。

教学简化包括：单主体可访问该服务配置下的全部会话、无跨服务进程协调、无可靠消息重放、无 Pi lease 全集、只提供有界展示历史。SQLite 和 Python 取消均沿用已有边界；`asyncio.to_thread` 包装的同步文件读取不能被声明为 OS 级可强制中断。M10 验证 owned asyncio tasks/连接/模型资源清理，异常阻塞文件系统与容器沙箱仍是生产差距。

## D. 首片练习与实现复盘

当前处于完整链路最外侧：**服务端从 TCP 获得字节块 → 帧解码 → DTO 校验 → 派发**。首片只连接前两个步骤。若把每次 read 当成一条消息，`R1` 的 JSON 可能只收到前半段便误报失败；若先按声明长度分配内存，恶意超大头部会耗尽内存。

Pi 使用 `FrameDecoder.push()` 在多次输入之间保存头/正文进度，并在头完整时检查上限。Python 保留这个状态机，采用 `bytearray` 存未完成数据；不需要 StateGraph、reducer 或 checkpoint，因为这是每个连接的瞬时解析状态，不能混入会话业务状态。

脚手架创建 `protocol/errors.py` 的 FrameError、`framing.py` 的构造/编码/finish/失败清理辅助方法、模块导出和 `tests/protocol/test_framing.py`；学习者完成的核心实现为：

```python
# 已实现的方法签名。
class FrameDecoder:
    def feed(self, chunk: bytes) -> list[bytes]: ...
```

- 输入：一个 bytes 块，可能为空、只有半个头、半段正文，也可能包含多个完整帧。
- 输出：本次新完成的 payload 列表，保持 wire 顺序，去掉四字节头；未完成数据留待下次 feed。
- 约束：固定四字节大端头；头完整后先检查 `1 <= length <= max_frame_bytes`，才接收正文；只累积实际收到的未完成数据，不按未校验长度预分配；ended/failed 不可复用；失败清空缓存；不解析 JSON、不碰文件和网络。
- 贯穿示例：将“请读取 probe.txt 并总结”的请求编码为 payload P；把 `encode_frame(P)` 按第 2 字节和第 7 字节切成三块，前两次 feed 返回 `[]`，第三次返回 `[P]`；随后接两个帧也应一次返回两个 payload。
- 测试意图：所有拆分位置证明 read 边界无关；粘包证明不会漏请求；UTF-8 多字节正文证明按 byte 计数；刚好上限/超限头证明边界与提前拒绝；EOF/失败后调用证明半消息不会交给业务。
- 验证命令：`uv run pytest tests/protocol/test_framing.py -q --basetemp=.pytest-tmp-m101`，然后执行 PLAN 的统一静态门禁。
- 完成条件：上述约束均有断言且通过；能解释已接收头字节数、预期正文长度、已接收正文字节数之间的关系。脚手架创建时记录实际测试数与红灯原因，本计划不预写通过数量。

实现审查：`feed()` 拒绝非 bytes 但不污染 open 状态；用 offset 逐步补齐 4 字节头；头完整后用无符号大端解析长度，先拒绝 0 和超限值；只把实际收到的正文片段追加到 `_payload`，没有按不可信声明长度预分配；正文齐备时复制为不可变 bytes、清理当前帧状态并继续解析同一输入中的下一帧。`_fail()` 将 decoder 置于终态并清空头/正文/预期长度，`finish()` 对残帧给出截断错误。状态保存在每连接 decoder 对象，不进入 checkpoint 或 AgentState。

验证结果：`uv run pytest tests/protocol/test_framing.py -q --basetemp=.pytest-tmp-m101` 为 **24 passed**；`uv run mypy src tests` 检查 207 个文件通过；`uv run ruff check .` 通过；`uv run ruff format --check .` 检查 248 个文件通过。练习实施前脚手架基线 11 passed、13 个 TODO 失败只记录为过程，不是最终结论。

### 当前端到端位置

贯穿请求仍是客户端提交 `prompt(session_id, text)`：TCP 任意字节块先由 M10.1 `FrameDecoder.feed()` 组合成完整 payload；本切片检查 UTF-8/JSON 和严格 client DTO；之后 M10.3 才认证并建立字节连接，M10.6 才能按握手阶段派发请求，M10.4/M10.5 才调用已有 async graph 并管理运行。此前完整帧只保证“字节数完整”，一个字段错误、方向颠倒、重复 JSON key 或非有限数都不能成为业务请求；DTO 成功也仍不代表已认证或可执行。

### Pi 设计到本项目代码

问题是完整 payload 仍是不可信数据。Pi 的 pinned [`schemas.ts`](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/protocol/src/schemas.ts) 用判别字段约束 hello、request、response 和 event；[`codec.ts`](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/protocol/src/codec.ts) 负责解析与编码时验证。Python 方案保留“先 parse、再按方向验证”的因果顺序，用冻结且 `extra="forbid"` 的 Pydantic DTO 表达公开合约；不把 LangGraph state/checkpoint 暴露到网络。JSON loader 另行拒绝重复 key 和非标准数值，避免普通 `json.loads()` 默认接受重复 key 或 NaN。

## G. M10.3 认证 transport 复盘

### 整体链路与当前断点

本项目远程链路是 client connector → 独立认证前导 → M10.1 帧边界 → M10.2 DTO → M10.6 握手与派发 → M10.4/M10.5 的共享运行器和 session ownership → graph/checkpoint → client pending 请求/权威快照。M10.1、M10.2 已完成；M10.3 只建立认证前置的 byte connection；认证成功也还没有 hello 协商或业务命令派发。如果没有本片，任何连上 TCP 的客户端都可能把未认证字节送入后续协议业务。

### 贯穿场景

客户端把 `4-byte big-endian length + UTF-8 token + hello + 后续业务帧` 一次 `write()` 给 loopback socket。server 先在 5 秒 deadline 内只读完整认证长度和 token；长度超过 4 KiB、为零、截断、超时或 token 不匹配都关闭且业务 callback 调用数为零。认证成功则把原 `StreamReader` 连同其缓冲区交给 callback；因为 gate 使用 `readexactly()` 只消费前导，紧随其后的 hello/业务字节仍能从同一 reader 读取。这条路径演示了 TCP read 分块并不等于认证前导边界，也说明 gate 不该自己新建/丢弃 reader。

### Pi 设计到 Python 选择

Pi pinned [`connection.ts`](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/server/src/connection.ts) 把 ByteConnection 表达为 server 可使用的已授权连接；listener 管 socket 生命周期。它并不意味着 Pi 使用此处的 bearer-token 前导。本项目为了单机 Windows 场景选择 `127.0.0.1` TCP 和独立 token frame：认证成功前不触达业务 callback，避免凭据进入 hello/request DTO、LangGraph state 或日志。

Python `protocol/transport.py` 给出 `AsyncByteConnection` 端口、asyncio stream 实现、四字节 auth length helper、token frame 编码、单 reader 约定、serialized writer 和 pending-byte/send/close 限额。`server/transports/tcp.py` 验证 loopback 地址、token 配置、连接数和 deadline，拥有 accept task/connection 并只在 gate 成功后调用 callback。`client/transport.py` 只连接 loopback，从 `PI_AGENT_REMOTE_TOKEN` 读取 token、先发送 auth frame，再返回 byte connection；它不发送 hello，也不重放业务请求。`server/auth.py` 负责读取/验证服务端 token 配置并提供本片的唯一练习入口。

### 学习者练习与实现复盘

请只实现 `src/pi_agent/server/auth.py` 中：

```python

    reader: asyncio.StreamReader,
    expected_token: bytes,
    *,
    timeout_seconds: float = DEFAULT_AUTH_TIMEOUT_SECONDS,
) -> bool: ...
```

- **输入**：一条 TCP `StreamReader`，服务端已校验的 token bytes，默认 5 秒认证期限。

- **失败规则**：将 timeout、EOF/截断、坏长度和错 token 统一返回 `False`；token 不进入错误文本或日志；未认证时业务 callback 必须保持零调用。deadline 同时覆盖 header 和 body。
- **脚手架协作**：`encode_auth_prelude()` 是 client 侧 wire helper；`load_remote_token()` 在 listener bind 前检查服务端凭据；`TcpByteServer` 仅在函数返回 True 后执行注入 callback，并负责关闭/释放连接；client connector 只发送前导。无需修改这些模块或添加第二个 TODO。

实际结果（2026-09-24）：学习者完成 `authenticate_connection()`，在统一 deadline 内使用 `readexactly()` 只消费认证前导，再用 `hmac.compare_digest()` 检查 token。完整切片测试 **16 passed**；mypy 检查 **221 source files**、Ruff lint、format **262 files** 全通过。复验期间 auth 注释中的全角标点曾触发 lint，已改成 ASCII 分隔符后全部门禁通过。用户另报告 `tests/server` **14 passed**，该子集不包含 client transport 测试。回到整体，请求目前抵达认证 byte connection；hello 与命令派发尚待 M10.6。M10.4 会复用当前 async graph 并投影 checkpoint；M10.5 再加入 run 所有权。

## I. M10.5 会话运行所有权与取消

### 整体链路与断点

贯穿场景仍是远程 prompt：“读取 `probe.txt` 并总结”。M10.1–M10.3 建立帧、DTO 和认证连接；M10.4 让 server 进入持久 async graph。现在若同一 session S 的 `run-1` 尚未结束，第二个 prompt 仍可能重入同一个 checkpoint。M10.5 在 graph 外维护 session→active run 映射：S 的重复请求立即 busy，独立 session T 仍可并行；cancel 必须匹配 run id，取消后先 join 资源清理再释放 S。

### Pi 设计与 Python/LangGraph 取舍

Pi 的 [`sessions.ts`](https://github.com/earendil-works/pi/blob/main/packages/server/src/sessions.ts) 让 `LiveSessionManager` 管 runtime 生命周期。`LiveSession.operationCount` 配合 `runOperation()` 的 `finally` 统计操作，`maybeDispose()` 只有在连接和操作都不再拥有 runtime 时才释放它。Python 项目不照搬连接 attach/detach/多 lease 面向；本片使用进程内 `SessionCoordinator` 和单 `RunLease`，LangGraph 继续拥有图状态，协调器只拥有 asyncio task 与 cancellation token。领取函数不 await，因此 check-and-set 在单 event loop 的同步区完成；这不提供分布式互斥。本片只限制每个 session 同时一个 run；server epoch/revision 是 M10.4 snapshot 边界的数据，全局连接和活动 run 上限由 M10.6 dispatcher 执行。

### 当前切片与失败路径

`try_claim_run(S, run-1)` 成功产生 lease；`try_claim_run(S, run-2)` 抛 `SessionBusyError`，而 T 可以单独获得 lease。`cancel_run(S, old-run)` 返回 not_found，不触碰当前 task。精确取消会 set token、cancel task，再在 cleanup deadline 内 join；超时返回 needs_recovery 且 S 仍被 lease 占用，task 真正退出后才由 done/finally 清理 lease。进程重启后内存 lease 消失，但 checkpoint 若尚有 `next` 节点，应用层只报告 needs_recovery，不自动重跑。

## J. M10.6 服务端协议派发

贯穿 request `R1` 在 M10.3 后已经认证、M10.1/10.2 后已经成为严格消息 DTO，但此前还没有协议 reader 和 ready 状态，所以它不能抵达 M10.4 runtime。M10.6 将这一截接通：`ServerConnection` 独占 read loop，`FrameDecoder` 处理任意分片/合并，`decode_client_message()` 校验方向与 schema；只有正确版本 hello 后才允许 request。入站 request ID 必须递增且不得重复；每个 accepted request 独立 task；同一 response/event writer 再调用 `encode_server_message()` 和 `encode_frame()`。断开时 phase 先进入 closing，取消并 join 所有连接拥有的 tasks，再关闭 transport。

Pi 的 server receive/dispatch/handshake/request handler 与 `sessions.ts::executeCommand()` 把网络状态、协议状态和 session runtime 分层。Python 对照源码链接见 [server.ts](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/server/src/server.ts)、[connection.ts](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/server/src/connection.ts)、[sessions.ts](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/server/src/sessions.ts)。Python 采用已验证的严格 JSON schema，而不是把 transport 或 Pydantic 类型塞进 LangGraph State。`ServerCommandService` 依赖 SessionCatalog、ServerSessionRuntime 与 SessionCoordinator；server epoch、workspace、database、模型都由服务端配置，不能来自 client command。

练习只实现 `ServerDispatcher.dispatch_message(request: ClientRequest, *, send_event: EventSender) -> ServerResponse`。四个 command 变体必须各自路由到 service；response 的 `request_id` 与 command 必须和入站一致；prompt 透传 `request_id` 与 event sender；已知 `ServerCommandFailure` 保留安全错误码和固定消息；未知异常统一 `internal_error`，不得回传异常文本。connection 层已处理 hello phase、重复/倒序 ID、每连接最多 8 个请求；service 已处理每 session 单 run 和全局活动 run 上限（默认 4）。

练习完成后，`ServerDispatcher.dispatch_message()` 路由 `create_session`、`get_snapshot`、`prompt`、`cancel` 四个命令；response 保留原 request ID/command，prompt 将 `run_started` 关联同一个 request，错误响应不泄露内部异常。代码审查期间发现断开竞态：shutdown 开始后，已有清理 await 会让出 event loop，其他 request task 可能稍后注册 run，而最初的 owned-run 快照看不到它。连接现于 `_send_request_event()` 首先检查 closing/closed；该检查和 owner 登记之间没有 await，因此进入关闭状态后不可能迟到地启动 prompt。新增 `test_disconnect_does_not_start_run_after_owned_run_cleanup_snapshot` 锁定该顺序。

## K. M10.7 最小客户端与权威快照

### A. 从面出发：请求现在能往返，但调用方还不能安全等结果

贯穿 `R1 = prompt(S, “读取 probe.txt 并总结”)`，同时发出 `R2 = get_snapshot(S)`。服务端可能先回 R2 再回 R1；客户端须分别按 request ID 完成调用并核对 command。prompt 完成后，服务端 response snapshot 是该 session 的权威状态；断开前未观察到 response 时，R1 是 outcome unknown，不能自动重放。重连后旧 connection generation 的延迟消息应丢弃；若 `server_epoch` 改变，旧 revision 计数不可用于新进程状态的比较。

### B. 进入点：pending、epoch/revision 与连接代次

Pi 源码对应 `packages/client/src/client.ts`：`#request()` 先登记 pending map 再发送；`#handleMessage()` 以 response ID 找到 pending，核对 command，更新 state 后 resolve/reject；未知响应会关闭连接；`#handleConnectionStateChange()` 断线时拒绝尚未完成的 pending。其 client README 将 server/response snapshot 定义为权威，progress event 不乐观改写快照。[Pi client.ts](https://github.com/earendil-works/pi/blob/main/packages/client/src/client.ts)、[Pi client README](https://github.com/earendil-works/pi/blob/main/packages/client/README.md)。这里检索到的是上游 main 页面；本项目可复现基线仍记录在 M0 pinned SHA。本片不照搬 Pi 的 CBOR、session lease 或 attach API，使用当前 v1 strict JSON DTO 和 Python `asyncio.Future`。

Python 分层为 `ClientConnection`（client hello、单 reader、framing）→ `RemoteClient`（四个 API、pending、deadline、响应边界）→ `ClientState`（generation、server epoch、revision、stale cache）。连接 generation 是本地 fencing token，server epoch 表示服务端进程 incarnation，revision 只在同 epoch 内比较，request ID 只用于 response correlation；这些值不互相替代，也不进入 LangGraph state。

**唯一学习者练习**：`src/pi_agent/client/client.py::RemoteClient.resolve_response(response: ServerResponse, *, connection_generation: int) -> None`。输入为已通过 wire codec 的 response 和接收连接 generation。练习负责按 ID 恰好取出 pending、command 匹配、未知/重复/mismatch 触发当前 connection protocol failure、将安全服务器 error 映射为 `ServerRejectedError`，并只在匹配的成功 response 带有 snapshot 时调用 `ClientState.apply_snapshot()` 后完成 Future。旧 generation 的响应忽略；不自动重试。测试保护乱序回包、prompt/cancel API、错误映射、未知/重复 ID、断线/timeout 的 outcome unknown、revision 防回退、新 epoch 重置和 stale generation fencing。

### C. 从点回到面：实现后的全链路与停点

### B. 进入点：composition root、transport conformance、子进程所有权

Pi 源码链路是 [`server.ts::Server.start/accept/close`](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/server/src/server.ts) 拥有 listener 与连接生命周期 → [`client.ts::PiClient.#request/#handleMessage`](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/client/src/client.ts) 关联公共命令和 pending response → [Pi client transport-neutral README](https://github.com/earendil-works/pi/blob/96317e50b8d6e7f6d0e47fd29122baf1461c00f5/packages/client/README.md) 让 ordered byte transport 由部署侧提供。本轮 pinned SHA 页面返回 GitHub cache miss；对照了上游 main 同路径，因此版本来源边界是明确的。

本项目因果映射：协议逻辑不应因 transport 类型而改变，所以 `ServerConnection/ServerDispatcher` 继续保持 byte port 与 service port；`server/app.py` 将已验证的 model config、workspace、SQLite catalog、coordinator、`ServerSessionRuntime` 和 `TcpByteServer` 组合；`client/app.py` 只负责 parse 参数、创建 `RemoteClient`、打印一份 snapshot JSON 和 finally-close。LangGraph 继续只拥有图 state/checkpoint，不负责 socket、进程信号、命令行或生命周期。

对同一 conformance use case 跑 memory transport 与 localhost TCP，期望 request/response semantics 完全一致；TCP case 额外通过 token prelude。再由真正 Python server/client subprocess 执行 fake read，杀死测试若使用 `terminate()` 会跳过 cleanup，因此 smoke 通过 SIGTERM/SIGBREAK 请求正常停机，再重启 listener 读取相同 SQLite。测试 token 仅为合成数据，并断言不出现在 stdout/stderr。

需要掌握的知识沿链路排列：

1. **Dependency wiring**：model、database、workspace、token 是 server-owned config，client 不得传路径、provider 或凭据。composition root 负责创建依赖，domain/service/runtime 不读取 CLI 全局变量。
2. **Lifecycle ownership**：server application 关闭 listener、连接 handler 和 provider client；一个已接受请求无法证明 server shutdown 完成，必须 join owned tasks 并检查进程退出码。
3. **Transport conformance**：协议 contract 对 memory/TCP 相同，只有连接 adapter/认证层不同；共享测试证明的是相同 server connection/dispatcher 行为，不代表任意网络传输可靠性。
4. **Durable resume**：server epoch 表示进程 incarnation，SQLite checkpoint 表示可继续读取的 session history；重启不能把 snapshot memory cache 当作唯一数据源或自动重跑已完成 prompt。
5. **安全诊断**：remote token 只读环境变量；argv、ready line、JSON snapshot、stderr 和 traceback 不出现 token/API key/provider body。绑定地址由 transport policy 固定 loopback；该边界没有设计公网监听。

实现后同一链路是：CLI 参数映射为 `RemoteClient` 请求 → server 认证/dispatch → fake tool 读取 probe → SQLite checkpoint 保存历史 → server 关闭重启 → client 重新查询既有 session snapshot。memory/TCP conformance、公开子进程 cleanup 和 restart smoke 证明了模块重新接回进程链路；本结果不覆盖公网、真实 compatible 模型质量、跨进程 lease/exactly-once 或 M11 threat/performance audit。

归档复验结果：`uv sync --all-extras` 通过（56 resolved、54 audited）；两个入口 help 通过；取消竞态与子进程日志聚焦 **5 passed**，TCP transport 关闭边界聚焦 **8 passed**；协议/server/client 组合 **133 passed**；全仓非 live 回归 **565 passed、4 deselected**；mypy **247 source files**、Ruff lint、format **289 files** 和 `git diff --check` 通过；fake JSONL CLI 与 eval smoke 均通过（1/1）。关机超时现在向上报告失败，不把仍在运行的 handler 当成已回收。pytest cache 产生一条权限警告，不影响测试。M10 已交付离线本机范围归档，M11 仍为 pending。

范围边界：本地 TCP + 进程 smoke 证明这台 Windows 上的 loopback、process cleanup 和 SQLite reopen，不证明外网部署、跨进程 session lease、exactly-once、真实 compatible 模型质量或 M11 threat/performance audit。当前 fake model 只负责发出 `read(probe.txt)` tool call 与 deterministic summary。归档后在此停止，不自动进入 M11。
