# M2 验收——消息、状态与最小图

状态：`completed`

## 目标及其在架构中的位置

M2 引入了最小且易于理解的 Agent 运行时：一条用户消息进入带类型的共享状态，一个注入的模型生成一条助手消息，再由一条显式条件边路由至 `END`。它建立了 M3 工具循环将复用的契约，但没有过早实现工具。

## 与 Pi 源码的对应关系

- `packages/ai/src/types.ts`：`UserMessage`、`AssistantMessage` 以及标准的 `Message` 联合类型。
- `packages/agent/src/types.ts`：`AgentMessage`、`AgentState` 以及 `convertToLlm` 投影边界。
- `packages/agent/src/agent-loop.ts`：`runLoop()` 调用 `streamAssistantResponse()`，追加助手消息，并在模型失败时以可观察的方式结束。

固定源码：`earendil-works/pi`，`main` 分支的 `96317e50b8d6e7f6d0e47fd29122baf1461c00f5`。

## 从 TypeScript 到 Python/LangGraph 的映射

| Pi 设计 | M2 实现 |
|---|---|
| `AgentMessage[]` | 使用 LangChain `AnyMessage` 的 `AgentState.messages` |
| 可变的消息追加 | 节点返回消息增量；由 `add_messages` 应用该增量 |
| `AgentState` | `TypedDict` 图状态 |
| `Agent` 上的模型/流式函数 | 通过 `RunContext` 注入的 `ChatModel` 协议 |
| 失败停止原因 | 可序列化的 `ModelError` 加 `failed` 状态 |
| 循环终止 | 返回 LangGraph `END` 的条件边 |

## 最小实现及其局限

假模型是同步且确定性的。图中只有一个模型节点、一条条件边，并且没有持久化。这里只接受标准 LangChain 消息；Pi 的自定义/UI 消息以及 `convertToLlm` 投影推迟到上下文里程碑实现。这里的流式输出只验证 LangGraph 状态更新，不验证计划在 M5 中实现的稳定应用事件 DTO。

后续的生产级工作将加入供应商适配器、取消、重试分类、token 流式输出、检查点、消息投影、遥测和敏感信息脱敏。这些都不属于 M2。

## 引导式练习

### 为什么需要这个节点

M2 的调用流程如下：

```text
HumanMessage
  -> AgentState.messages
  -> model_node 读取累积的消息
  -> RunContext 提供模型依赖
  -> ChatModel.invoke 返回 AIMessage
  -> model_node 返回状态增量
  -> add_messages 合并该增量
  -> route_after_model 观察 completed/failed 状态
  -> END
```

在 Pi 中，`streamAssistantResponse()` 接收当前的 `AgentContext`，应用 `transformContext` 和 `convertToLlm`，调用已配置的流式函数，并通过生命周期事件追加最终得到的助手消息。M2 保留了可序列化会话状态与模型依赖之间的重要分离，但将流式输出和自定义消息投影简化为一次同步的假模型调用。

因此，`model_node` 并不是一个孤立的辅助函数：它是累积的 Agent 状态与模型执行之间的边界。它有意返回增量，因为 LangGraph 会应用 `add_messages`；如果返回完整历史记录，用户输入将被再次追加。它的错误分支会把 Python 异常转换为图状态，使路由逻辑和调用方能够观察到一个正常的失败终止状态。

### 你的实现任务

只实现 `src/pi_agent/graph/nodes.py` 中的 `model_node`。

契约：

1. 使用 `state["messages"]` 调用 `runtime.context.model.invoke(...)`，且只能调用一次。
2. 成功时，`messages` 中只返回新的助手消息；不要拼接现有状态，因为 `add_messages` 是归约器。
3. 成功时将 `status` 设为 `completed`，并清空 `error`。
4. 捕获模型异常并返回 `status="failed"`，其中包含错误码、异常类型和消息。不要添加消息，也不要泄露堆栈跟踪。

## 回到整体

仍以相同的 `"hello"` 场景为例，仓库已经从一个可安装的项目骨架演进为具备最小 Agent 心跳的系统：

```text
HumanMessage("hello")
  -> AgentState(status="ready")
  -> model_node
  -> FakeChatModel.invoke(messages)
  -> 作为状态增量的 AIMessage("hello from fake")
  -> add_messages
  -> AgentState(status="completed", messages=[HumanMessage, AIMessage])
  -> route_after_model
  -> END
```

发生失败时，同一条路径会以 `status="failed"` 结束，保留 `HumanMessage`，并公开 `ModelError`。LangGraph 提供状态传播、归约器应用、节点执行和路由；应用代码仍负责消息契约、依赖边界、错误语义和测试。

M2 有意保持为一个单轮、无工具的图。M3 现在可以扩展 `AIMessage` 之后的决策：不含工具调用的消息仍然到达 `END`，包含工具调用的消息则路由到工具节点，然后返回模型。此验收记录并不代表 M3 已经开始。

## 学习归档

本节是可长期保留的 M2 复习记录。只有当学习者能够从端到端流程解释以下契约，而不只是复现语法时，才算真正掌握 M2。

### 必须掌握的知识

1. **图执行模型**：`State` 是累积的快照；节点执行一个工作单元并返回部分更新；归约器合并该更新；边选择下一个节点。
2. **状态与更新的区别**：`model_node` 读取完整的消息历史，但只返回新生成的助手消息。`AgentStateUpdate(total=False)` 明确表达了这个部分更新契约。
3. **消息归约器语义**：`add_messages(left, right)` 会追加具有新 ID 的消息，并替换 ID 相同的已有消息。它比只会拼接列表的 `operator.add` 语义更丰富。
4. **运行时依赖边界**：`RunContext.model` 为单次调用注入，不属于会话数据。消息、状态和可序列化错误应放在 `AgentState` 中；模型客户端、凭据和连接则不应放入其中。
5. **显式控制流**：`route_after_model` 读取应用归约器之后产生的状态。在 M2 中，它只允许 `completed` 或 `failed` 终止状态，然后返回 `END`。
6. **稳定的失败契约**：供应商异常会被转换为可序列化的 `ModelError`；消息历史得到保留，且不存储堆栈跟踪。这样，调用方和后续路由就能观察失败，而不依赖供应商特定的异常。
7. **确定性的边界测试**：`FakeChatModel` 证明哪些消息确实跨越了模型边界，图测试则分别证明最终累积状态和节点的流式更新。

### 重写中继承的 Pi 设计

Pi 的 `runLoop()` 将助手响应、工具执行和下一轮决策保留在一个命令式循环中。M2 把第一段提取为显式的 LangGraph 契约：

```text
Pi：        AgentContext -> streamAssistantResponse -> 追加助手消息 -> 停止/继续
LangGraph： AgentState   -> model_node              -> 归约器       -> 条件边
```

该实现保留了 Pi 对会话数据与已配置模型运行时的分离。它有意将 `transformContext`、`convertToLlm`、token 流式输出、工具执行和会话存储推迟到计划中的后续里程碑。

### 复习问题与答案要点

1. **为什么 `model_node` 返回 `[reply]`，而不是完整历史记录？**
   - 节点返回的是状态更新，而不是替换用的完整快照。
   - `add_messages` 将现有消息作为 `left`，将节点更新作为 `right`。
   - 再次发送完整历史在语义上是错误的；当消息 ID 缺失或变化时，可能产生重复消息。相同的 ID 可能通过替换消息掩盖这一错误，因此代码不能依赖这种偶然现象。
2. **为什么模型存放在 `RunContext` 中，而 `status` 存放在 `AgentState` 中？**
   - 模型是一次调用所需的依赖，可能包含客户端、凭据、回调或其他不可序列化资源。
   - `status` 是路由、调用方、检查点和后续恢复都需要的执行事实。
3. **与 `operator.add` 相比，`add_messages` 还提供了什么？**
   - 两者都能追加全新的消息。
   - `add_messages` 还能按 ID 识别现有消息并替换它们，从而支持修正以及人在回路中的状态编辑。
4. **M3 应该在哪里分支到工具执行？**
   - 在 `model_node` 执行并应用归约器之后，因为只有这时，状态中才存在最新的 `AIMessage.tool_calls`。
   - 没有工具调用则到达 `END`；有效调用路由到工具节点；追加工具结果后再返回模型。
5. **为什么要把模型异常转换为状态，而不是总让异常向外抛出？**
   - 稳定的图终止状态具有可观察性和可测试性，并且不依赖供应商异常类型。
   - 在后续生产级里程碑中，仍应把非预期的框架/编程错误与预期的供应商失败处理区分开。


## 常见错误与安全说明

- 返回 `state["messages"] + [reply]` 会错误地把旧状态当作新增量重放。当消息 ID 不同或缺失时，这可能重复输入；相同 ID 则可能通过替换行为掩盖该问题。
- 将模型对象放入 `AgentState`，会把运行时依赖与可序列化的会话状态混在一起。
- 让模型异常向外抛出，会破坏稳定的失败状态契约。
- 在状态中包含堆栈跟踪可能泄露路径或敏感的供应商细节；M2 中只存储异常类和消息。
