## B. 当前纵向切片：读取工作区文件

### B1. 同一请求的成功和失败路径

成功请求：模型调用 `read(path="README.md")`。

1. registry 找到 read tool 并用 Pydantic 校验参数。
2. read tool 把模型提供的路径交给 `WorkspacePathPolicy.resolve()`。
3. policy 从固定工作区根目录解析真实规范路径，证明目标仍位于根目录内。
4. read tool 读取文件并按字符/字节预算截断。
5. registry 生成与原 call ID 关联的 `ToolMessage`，模型继续回答。

失败请求：模型调用 `read(path="../secret.txt")`，或工作区内路径经过符号链接指向外部文件。

1. 参数在语法上可能完全合法，因此 Pydantic 校验不能替代权限检查。
2. policy 对规范化后的真实路径做目录成员关系判断。
3. 路径越界时在文件读取前抛出稳定 `PathPolicyError(code="outside_workspace")`。
4. 后续接入 registry 时，该错误会成为可恢复的工具结果，模型可以改用工作区内路径；任何外部文件都未被读取。

### B2. 为什么先做这个点

read、list、search、write 和 edit 都接收路径。如果各工具分别拼接字符串或只检查 `..`，规则会漂移，而且无法防住绝对路径、同名前缀目录和符号链接。先建立唯一的路径门禁，后续文件工具只负责自身业务。

### C2. 必须掌握

1. **路径拼接不等于目录约束**：`root / user_path` 仍可能被 `..` 或绝对路径绕过。
2. **字符串前缀不等于目录成员关系**：`C:\work-backup` 不是 `C:\work` 的子目录。
3. **lexical path 不等于 canonical path**：符号链接可以让表面位于工作区内的路径解析到工作区外。
4. **读和写的存在性不同**：读取要求目标已存在；写入可以指向尚不存在的文件，但其可解析父路径仍必须留在根目录内。
5. **校验应早于副作用**：参数、权限、风险和审批任何一步失败，都不应先部分写文件或启动进程。
6. **审批恢复会重放节点**：`interrupt()` 需要 checkpointer 和稳定 `thread_id`；`Command(resume=...)` 恢复时节点从头执行，因此 interrupt 之前只能做确定、幂等或无副作用的工作。
7. **主机权限不是 Agent 权限**：操作系统账户能访问某个路径，不代表模型被授权访问它。

## D. 唯一学习任务：实现工作区路径门禁

- 目标文件：`src/pi_agent/security/path_policy.py`
- 目标签名：`WorkspacePathPolicy.resolve(self, requested_path: str, *, must_exist: bool = True) -> Path`
- 输入：模型提供的相对或绝对路径；读取时 `must_exist=True`，预备写入时为 `False`。
- 输出：规范化、绝对且确认处于 `self.root` 内的 `Path`。
- 错误：空白/NUL 和非“缺失”类解析故障抛 `PathPolicyError("invalid_path", ...)`；必需目标不存在抛 `not_found`；任何越界抛 `outside_workspace`。
- 约束：不得用字符串 `startswith`；不得只搜索 `..`；必须检查解析后的路径目录关系；不得访问文件内容、创建目录或文件；不要修改 registry、图或具体工具。
- 特别边界：相对路径、工作区内绝对路径、`..`、同名前缀 sibling、符号链接逃逸、允许工作区内尚不存在的写目标。
- 测试：`tests/security/test_path_policy.py`。
- 预期结果：初始脚手架为 `1 passed, 10 failed`；学习者首次实现后原有 `11 passed`。安全审查新增非“缺失”类解析错误分类测试，修正后应为 `12 passed`，且符号链接/Windows junction 防护不得跳过。
- 验收条件：`uv run pytest tests/security/test_path_policy.py -q` 和 `uv run mypy src/pi_agent/security tests/security` 均通过，然后由助手审查安全语义，再进入本里程碑的具体工具阶段。

## F. 第二切片：read/list/search 与统一输出预算

### F1. 从面到当前点

贯穿请求是“先列出项目根目录，再搜索 `LangGraph`，最后读取 README 的命中窗口”。它在系统中的位置是：

```text
AIMessage.tool_calls
  -> ToolRegistry / Pydantic
  -> WorkspacePathPolicy                  已完成
  -> read / list / search                 当前切片
  -> TextOutputBudget                     当前下钻点
  -> ToolMessage / add_messages / model   M2-M3 已完成
```

list/read/search 都是只读能力，不需要 HITL；它们必须共用路径门禁和结果预算。越界路径在访问前失败，目录和文件类型不匹配会成为工具执行错误，合法结果在进入 `ToolMessage` 前完成截断。

### F2. Pi 设计与 Python/LangGraph 映射

- Pi `packages/agent/src/harness/types.ts:FileSystem` 把 `readTextLines`、`listDir`、`canonicalPath` 和稳定 `FileError` 放到执行环境边界；本项目当前直接使用本地 `Path`，但把授权放在独立 `WorkspacePathPolicy`，未来仍可替换文件系统适配器。
- Pi `harness/tools/read.ts:createReadTool()` 先解析路径，再读取 UTF-8/二进制，支持 1-based offset/limit，并在结果中给出继续读取提示。本切片只支持 UTF-8 文本，保留 offset/limit，图片和二进制留作非目标。
- Pi `harness/utils/truncate.ts:truncateHead()` 用独立的行数/UTF-8 字节数限制，谁先达到就按谁截断，并避免半行。本项目用 `TextOutputBudget` 让 read/list/search 共享这条约束。
- 当前可核验的 Pi 快照没有独立 search 工具源码；本项目的 search 是规格要求新增的 literal search，限制扫描文件数和匹配数，不使用任意 shell，也不把正则 ReDoS 风险引入第一版。
- LangGraph 不负责文件遍历或输出安全。现有 tool node 仍只调用 registry、将结果作为消息增量交给 `add_messages`；具体 I/O、预算和错误归一化属于应用层。

### F3. 唯一学习任务：实现统一文本输出预算

- 目标文件：`src/pi_agent/tools/output.py`
- 目标签名：`TextOutputBudget.apply(self, text: str) -> BoundedText`
- 输入：read/list/search 即将返回给模型的完整文本。
- 输出：最大的“从头开始、只包含完整行”的 `BoundedText`，同时记录原始/输出行数和 UTF-8 字节数、截断原因及首行超限标志。
- 约束：空文本为 0 行/0 字节；字节数必须使用 UTF-8 编码计算，不能使用 `len(text)`；行数和字节数任一先到即停止；不得返回半个 Unicode 字符或半行；第一行本身超出字节预算时内容为空且 `first_line_exceeds_budget=True`；未截断时必须原样返回输入。
- 脚手架协作：`read_only.py` 的三个 handler 都在真实只读操作后调用 `apply().render()`；factory 把它们包装为 M3 的 `ToolDefinition`；registry 和图无需知道预算细节。
- 测试：`tests/tools/test_output.py` 直接保护预算算法，`tests/tools/test_read_only.py` 证明预算实际位于 read/list/search 到 registry 的返回路径上。
- 脚手架实际结果：目标 Ruff lint、9 个文件格式检查和 mypy 全部通过；既有 M3/M4 回归 `25 passed`。新切片为预期的 `3 passed, 9 failed`，九个失败全部指向唯一 `TextOutputBudget.apply()` 的 `NotImplementedError`。
- 完成标准：`uv run pytest tests/tools/test_output.py tests/tools/test_read_only.py -q --basetemp=.pytest-tmp` 与 `uv run mypy src/pi_agent/tools tests/tools` 全部通过，随后由助手审查并回到完整 `list -> search -> read -> model` 链路。

### F4. 教学简化与后续边界

- read 当前一次读入完整文本，输出虽有界但内存工作量仍可能较大；生产版应流式读取并设置输入上限。
- search 是 literal UTF-8 search，跳过无法读取/解码的文件，并独立限制扫描文件数与匹配数；glob、ignore 规则、二进制检测和取消留作后续加固。
- 路径检查到打开文件仍存在已记录的 TOCTOU；具体 handler 不缓存授权路径。
- 本切片不含 write/edit、命令、interrupt/checkpointer 或 M5 streaming。

## H. 第三切片：edit/write 的无副作用变更准备

### H1. 回到完整链路

```text
用户请求
  -> model 生成 edit/write tool call             M2-M3 已完成
  -> schema + WorkspacePathPolicy               M3/M4 已完成
  -> prepare FileChange proposal                当前切片
  -> approval node / interrupt                   下一子切片
  -> 版本复核 + atomic apply                     下一子切片
  -> bounded ToolMessage -> model                M3 契约
```

没有 prepare 层时，审批节点只能展示原始参数，无法证明旧文本是否唯一、目标是否越界、文件是否为 UTF-8，也无法记录用户批准的是哪个文件版本。更危险的是，如果在同一函数中先写文件再 `interrupt()`，恢复会重跑节点并重复副作用。

### H2. 贯穿场景和边界

成功场景：模型要求把 `README.md` 中唯一的 `M1 establishes the package.` 替换为 `M1-M4 establish the core loop.`。

1. Pydantic 建立 `EditArguments`，不允许额外字段。
2. `WorkspacePathPolicy` 把 `README.md` 解析为工作区内 canonical path。
3. `FileChangePlanner` 以 UTF-8 读取且保留 BOM、LF/CRLF，记录原内容 SHA-256。
4. `apply_exact_replacement()` 证明 `old_text` 恰好出现一次并派生新内容，但不写文件。
5. 后续 approval node 才把可序列化 proposal 交给 `interrupt()`；批准后 apply node 复核版本并落盘。

失败路径必须全部发生在审批和写盘之前：空 `old_text`、零匹配、多匹配、重叠匹配、no-op、目录目标、非 UTF-8、读取失败和工作区逃逸。

当前非目标：生成 diff、持久化 proposal、调用 `interrupt()`、临时文件 + `os.replace()` 原子写入、同路径并发队列、命令执行。它们不能绕过本切片，而是在唯一替换契约通过后逐步接入。

### H3. Pi 源码到 Python/LangGraph 的映射

| 问题 | Pi 设计 | 本项目改造 | 原因 |
|---|---|---|---|
| 完整写入 | `harness/tools/write.ts:createWriteTool()` 解析路径后调用 `env.writeFile()` | `prepare_write()` 只生成目标内容和已有版本摘要 | 审批前不得创建目录或文件 |
| 精确编辑 | `harness/tools/edit.ts:createEditTool()` 要求每个旧文本唯一、非重叠，并保留 BOM/行尾 | 首版一次只允许一个 exact replacement；先把最小语义学透 | 避免一次练习同时承担批量冲突算法 |
| 同路径并发 | `file-mutation-queue.ts:withFileMutationQueue()` 按环境 + canonical path 串行 | apply 子切片再加入 canonical-path lock | prepare 是纯读取/计算，不应提前引入锁 |
| 权限与审批 | Pi 默认继承启动进程权限 | `prepare -> approval node -> apply node` | 工作区权限和人工批准是本项目额外产品边界 |
| 恢复重放 | Pi 不是 LangGraph checkpoint 模型 | approval node 单独 `interrupt()`，副作用放后续节点 | LangGraph 恢复会从被中断节点开头重跑 |

当前 registry 用 `except Exception` 把 handler 故障转换成 `ToolMessage`；本地 `GraphInterrupt` 也属于 `Exception`。因此不能把 `interrupt()` 直接塞入现有 mutation handler，否则中断会被误报成普通工具失败。后续将新增独立 approval node，并使用 checkpointer 与稳定 `thread_id`。

### H4. 脚手架如何协作

- `WriteArguments` / `EditArguments`：模型参数边界。
- `WorkspacePathPolicy`：在任何文件读取之前拒绝越界。
- `FileChangePlanner`：读取现有版本并生成 `PreparedFileChange`；不得写文件。
- `PreparedFileChange.before_sha256`：为后续“批准后版本是否变化”提供依据。
- `apply_exact_replacement()`：本次唯一学习者 TODO；只处理纯字符串变换。
- `tests/tools/test_file_mutation.py`：证明 prepare 无副作用，并把七类精确替换约束固定为测试。

### H5. 唯一学习任务

- 目标文件：`src/pi_agent/tools/file_mutation.py`
- 目标签名：`apply_exact_replacement(original: str, old_text: str, new_text: str) -> str`
- 输入：文件原始 UTF-8 文本、要求唯一出现的旧文本、替换后的新文本。
- 输出：只替换该唯一片段后的完整字符串；不得修改文件或任何外部状态。
- 稳定错误：
  - 空 `old_text`：`FileMutationError("empty_old_text", ...)`
  - 找不到：`match_not_found`
  - 找到第二处（包括重叠匹配）：`match_not_unique`
  - `old_text == new_text`：`no_change`
- 约束：不要使用 `str.replace(old_text, new_text)` 后再猜替换次数；必须显式找到第一处和从“第一处起点 + 1”开始的第二处，才能识别 `original="aaa", old_text="aa"` 的重叠歧义。成功时用切片组装结果，保留 BOM、CRLF/LF 和所有未修改字符。
- 测试：`tests/tools/test_file_mutation.py`
- 当前预期：`3 passed, 7 failed`；七个失败全部来自该 TODO。
- 验证命令：

```powershell
uv run pytest tests/tools/test_file_mutation.py -q --basetemp=.pytest-tmp
uv run mypy src/pi_agent/tools tests/tools
uv run ruff check src/pi_agent/tools tests/tools
uv run ruff format --check src/pi_agent/tools tests/tools
```

- 完成标准：目标测试全部通过；不得删除或弱化失败路径；既有回归继续通过。完成后由助手审查错误优先级、重叠匹配语义和内容保真，再把 prepare 接到可序列化 proposal 与 approval node。

### H6. 完成结果与回到整体

学习者实现采用两次 `find()`：第一次定位唯一候选，第二次从 `match_offset + 1` 开始寻找，因此不会漏掉 `original="aaa", old_text="aa"` 的重叠歧义；找到第二处即可失败，无需收集所有匹配位置。该实现保持线性扫描量和常量额外空间，且原样保留未修改内容。

2026-09-16 复验：目标测试 `10 passed`；既有 domain/graph/security/tools 回归 `55 passed`；mypy、Ruff lint 和 Ruff format 均通过。`prepare` 现在能在无副作用条件下产出确定版本的变更提案，完整链路的下一个断点正式移动到 approval node。

## I. 第四切片：独立 approval node

### I1. 从整体定位当前断点

```text
PreparedFileChange                         已完成
  -> checkpoint-safe PendingFileChange    本切片脚手架
  -> file_approval_node / interrupt       当前唯一 TODO
  -> Command(resume=approve|reject)       本切片验收
  -> approval_status delta                本切片验收
  -> 版本复核 + atomic apply              下一子切片
  -> ToolMessage -> model                 M3 已完成
```

没有该节点时，prepare 只能说明“这是一份合法提案”，不能说明“用户批准了这份具体提案”。approval node 必须独立于当前 registry：registry 的通用 `except Exception` 会捕获同属 `Exception` 的 `GraphInterrupt`，而 LangGraph 从中断恢复时会从节点开头重跑。独立且无副作用的节点同时解决异常边界和重放安全。

### I2. 同一场景如何流过节点

以编辑 `README.md` 为例：上游把 operation、canonical workspace path、before/after SHA-256、完整 `after_text` 和有界 preview 写入 `PendingFileChange`。首次以稳定 `thread_id` 调用图时，节点发出 JSON 可序列化的审批请求并暂停；完整 `after_text` 仍只保留在 checkpoint state，中断 payload 只展示 operation/path/hash/preview。

恢复必须使用相同 `thread_id` 和 `Command(resume=...)`：

- `{"decision": "approve"}` 只把状态改为 `approved`；仍不写文件。
- `{"decision": "reject", "reason": "Wrong target file"}` 把状态改为 `rejected` 并保留原因。
- 非 pending 状态、非法 decision 或多余字段必须失败，不能悄悄批准。

后续 apply 节点只接受 approved 状态，先用 `before_sha256` 复核磁盘版本，再执行原子替换。本切片明确不包含这一步。

## J. 第五切片：批准后的版本复核与 atomic apply

### J1. 从整体定位当前断点

```text
prepare proposal -> approval interrupt/resume       已完成
  -> approved FileApprovalState                     当前输入
  -> re-resolve + before_sha256 check               当前 TODO
  -> same-directory temp + flush/fsync + os.replace 当前 TODO
  -> AppliedFileChange -> ToolMessage               下一接入点
  -> controlled argv process                         后续 M4 子切片
```

审批只证明用户批准了某个 checkpoint 中的 proposal，不证明磁盘仍是同一版本。apply 必须重新通过 `WorkspacePathPolicy` 解析路径，并在任何写入前比较当前内容哈希；否则用户批准后由其他进程修改文件时，旧 proposal 会覆盖新内容。

### J2. 贯穿场景与失败路径

对已批准的 `README.md` edit：

1. 从 `FileApprovalState.pending_change` 读取 operation/path/before hash/after text。
2. 按 operation 重新解析路径：edit 要求目标存在，write 允许新文件但仍要求父目录在 workspace 内。
3. 读取当前 UTF-8 文本并计算 SHA-256；与 `before_sha256` 不一致时以稳定 `version_changed` 错误失败，目标内容保持不变。
4. 将完整 `after_text` 写入目标同目录临时文件，使用 `newline=""` 保留 BOM/CRLF/LF，flush 并 fsync。
5. 用 `os.replace()` 将临时文件原子替换到目标，返回 canonical path、实际 before hash 和 after hash。

未批准、路径越界、目标类型错误、非 UTF-8、版本变化、临时文件写失败和替换失败都不得留下半写入目标；临时文件必须在异常路径清理。当前不做权限模式复制、跨文件批量事务或平台句柄级 TOCTOU 完全消除。

### J3. 模块协作和设计取舍

- `tools/file_apply.py:AppliedFileChange`：稳定的成功结果 DTO，不把文件内容重新复制到 ToolMessage。
- `tools/file_apply.py:apply_approved_file_change()`：唯一学习者 TODO；它是副作用边界，必须消费已批准 state，而不是重新相信模型原始参数。
- `WorkspacePathPolicy`：apply 前再次授权 canonical path；LangGraph checkpoint 不替代路径安全。
- `FileMutationError`：沿用工具层稳定错误契约；版本冲突应与读取/写入 I/O 错误分开，便于模型或上层决定是否重新 prepare。
- LangGraph 只负责把 approved state 路由到该边界；原子文件语义、临时文件清理和版本校验属于应用工具层。

### J4. 唯一学习任务

## K. 第六切片：结构化 argv 受控进程

### K1. 从整体定位当前断点

```text
model tool call -> schema/path/approval -> file apply       已完成
                                       -> argv process       当前 TODO
                                       -> allowlist + no shell 当前 TODO
                                       -> timeout/tree kill  当前 TODO
                                       -> bounded ProcessResult -> ToolMessage
```

文件能力已经有 workspace 和人工审批边界，但命令能力若直接接收 shell 字符串，就会重新引入任意命令、环境展开和管道注入。首版只接受结构化 `executable + argv + timeout_seconds`，由应用层决定 allowlist、cwd 和超时策略；不提供 PowerShell/bash 字符串入口。

### K2. 贯穿场景和失败路径

测试场景使用当前 Python 解释器作为显式 allowlist 成员：

1. Pydantic `ProcessArguments` 拒绝额外 `shell` 字段，模型无法把任意 shell 开关带入工具。
2. 不在 allowlist 的 executable 在 spawn 前失败。
3. 合法列表参数以 `shell=False` 启动，`literal;not-a-command` 只作为一个 argv 值，不会被解释为命令。
4. 超过 `timeout_seconds` 时终止进程（以及其子进程树），返回稳定 `timeout` 错误，不留下悬挂任务。
5. stdout/stderr 以 UTF-8 捕获并在进入 ToolMessage 前应用已有 `TextOutputBudget`；本切片先固定执行/错误边界，输出预算接入可作为同一函数内的低风险补全。

失败路径包括 executable 未授权、cwd 无效、spawn 失败、超时和非零退出。非零退出是结构化结果而不是 Python 异常；策略错误和执行错误必须可区分。

### K3. Pi 映射与安全取舍

- Pi `harness/tools/bash.ts:createBashTool()` 通过 `env.exec()` 执行命令并支持 timeout/取消；本项目不复制其任意 shell 文本入口，只保留受控执行和结果回灌思想。
- Pi `harness/env/nodejs.ts` 负责超时、AbortSignal 和进程树终止；Python 版本在本函数内明确 `Popen`、超时和 Windows 进程组/树终止策略。
- allowlist 和 cwd 是应用策略，不由 LangGraph 自动提供；LangGraph 只负责节点/工具路由。
- 进程 stdout/stderr 是不可信模型上下文，必须复用 `TextOutputBudget`，不允许无限制回灌。

### K4. 唯一学习任务

- 目标文件：`src/pi_agent/tools/process.py`
- 目标签名：`run_controlled_process(args: ProcessArguments, *, allowed_executables: frozenset[str], cwd: str) -> ProcessResult`
- 输入：严格结构化 executable、argv、正数且不超过 30 秒的 timeout、显式 allowlist 和 workspace cwd。
- 输出：`ProcessResult(returncode, stdout, stderr, timed_out)`；非零退出保留结果，不把普通命令失败伪装成审批错误。
- 实现顺序：
  1. 在 spawn 前检查 `args.executable` 是否精确属于 allowlist。
  2. 用 `[args.executable, *args.argv]` 和 `shell=False` 调用 `subprocess.Popen`，设置 cwd、捕获 stdout/stderr 和 UTF-8 解码策略。
  3. 用 `communicate(timeout=...)` 等待；超时先终止进程树，再回收 pipes，抛出 `ProcessExecutionError("timeout", ...)`。
  4. 将 `FileNotFoundError`/权限等 spawn 故障映射为 `execution_failed`；非零 returncode 仍返回 `ProcessResult`。
  5. 对 stdout/stderr 应用 `TextOutputBudget` 或明确的字符/字节上限，避免模型上下文被进程输出耗尽。
- 约束：不得 `shell=True`；不得接受拼接后的 shell 字符串；不得把任意 cwd 直接交给进程；不得无限等待或吞掉超时；不得记录环境变量中的密钥。

- 完成标准：五项测试全部通过；未授权命令不 spawn，argv 不经过 shell，超时得到稳定错误且进程被回收；非零退出和 stdout/stderr 结果可预测。完成后由助手补充输出预算和 Windows 进程树证据，再进入 M4 最终 HITL 集成。
