## 1. 从整体回看 M7

贯穿场景：在 `packages/agent` 中继续一段包含文件修改记录的长对话。M6 从 SQLite 恢复完整历史；M7 加载明确配置的全局规则和 workspace 祖先规则，装配本轮模型上下文。如果超过阈值，先摘要完整的旧历史并保留文件操作事实，再校验最终预算。模型/工具循环继续，checkpointer 只保存原始对话和新产生的消息。

```text
M6 原始历史 + 当前输入
  → 全局规则 / workspace 根到活动目录规则
  → prompt template 装配
  → 完整历史的压缩计划（保护最近 turn 和工具批次）
  → 可选摘要生成 + 文件操作事实
  → 最终 bytes / estimated tokens 门禁
  → model_node → 模型 / 工具循环 → M6 checkpoint
```

规则、摘要和被选中的历史只属于本轮派生上下文。上下文准备失败会产生 `context_error`，主模型不被调用；新用户输入及失败状态仍正常形成 checkpoint，旧消息和旧 checkpoint 不被覆盖。随后可以关闭 SQLite、重新打开并以修正后的配置继续会话。

Pi 设计映射沿用 M0 源码分析基线：coding-agent resource loader 管资源，Agent 的 `transformContext` 管模型可见消息。本项目由 `context/` 提供装配与摘要阶段，`RunContext` 注入依赖，`model_node` 在主模型前执行。摘要生成采用节点内同步阶段而非新增持久状态的独立图节点；因此既能接入 `ChatModel`，又无需把派生上下文写进 reducer/checkpoint。

LangGraph 的历史管理需要保持工具请求与结果完整，参见 [官方 memory 文档](https://docs.langchain.com/oss/python/langgraph/add-memory)。本项目复用既有同步节点和 checkpointer API，未迁移依赖或引入该文档其他版本的 streaming API。

## 2. 原计划范围与交付映射

| 原范围 / 验收要求 | 交付与证据 |
|---|---|
| 全局、祖先、当前目录 AGENTS.md | `global_instruction_file` 显式配置；workspace 只扫描根到活动目录；先 global 后 root→leaf，重复 canonical 文件去重。全局配置由调用者提供，不隐式扫描 home |
| prompt template、顺序可解释 | `prompt_template` 唯一 `{instructions}` 插槽；来源路径按顺序渲染；已有系统消息和原始历史保留 |
| token 估算、压缩阈值 | UTF-8 content/tool 参数计数；每消息 ceil(bytes/4)+4 的启发式 token 估算；`max_tokens` 和 `compaction_threshold_tokens` 明确区分 |
| 摘要生成阶段 | `Summarizer` 协议 / `ModelSummarizer` 使用已有 `ChatModel`；阈值或预算触发，fake model 实测输入与输出；旧的 supplied summary 接口保留 |
| 最近 turn 与文件操作事实 | `keep_recent_turns` 默认保护最近完整一轮；最少消息数可扩大保护范围；旧工具参数、路径、结果和状态作为历史数据随摘要保留 |
| 原始记录不删除 | SQLite 成功/失败、旧 checkpoint 按 ID 回读、关闭重开及续聊测试；持久消息不含临时规则或摘要 |
| 压缩失败不破坏会话 | 空摘要、摘要异常、摘要后超限、规则编码/路径失败均停止主模型；可在新一轮恢复 |
| 工具调用边界合法 | planner 与 budget 共享批次边界；多调用/逆序结果、不匹配 ID、未闭合调用、配置上下文的真实 tool graph 二次模型调用 |
| 上下文快照诊断 | `PreparedContext.diagnostic()` 与 `pi-agent context inspect --provider fake` 使用同一管线；显示路径/roles/尺寸/估算/压缩数量，默认不输出规则或提示正文 |

非目标保持原计划：Pi 的全部 skills/extensions 格式、精确 token 计费。真实 provider、异步流、超时与取消仍由 M8 承接。

本轮闭合的问题：

1. 原先先裁剪再摘要会丢失摘要输入。现在压缩计划基于完整装配历史，最终预算在摘要注入后校验。
2. 原先直接取 `BoundedContext.messages` 会吞掉 `over_budget`。现在必需规则、摘要或最近 turn 放不下就明确失败，不发送超限上下文。
3. 原先 budget 仍按单消息裁剪，planner 的工具配对修复无法补回已丢的请求。现在共享工具批次边界，并计入请求参数；非法关联明确拒绝。
4. 原先缺少摘要生成和文件事实保留。现在摘要适配器获得旧历史的深拷贝，事实另行原样保留；预算模式丢弃旧对话时也保留工具事实。
5. 原先只验证 graph 返回值，未实测 SQLite 原记录。现已覆盖旧 checkpoint 回读、失败落盘、重开、续聊。
6. 原先诊断入口缺失，验收文档新旧章节交错。现在入口可执行，当前状态只保留一份，历史移入快照。

## 5. 验收边界与后续归属

- token 是确定性的启发式估算，不等于供应商实际计费/上下文容量；图像、音频的隐藏 payload 开销不作精确测量。供应商 tokenizer 和多模态预算精度需在 M8/M9 验证。
- 同步摘要生成已通过 fake 测试；真实 LLM 的摘要语义质量、重试、超时、取消尚未验证，归 M8/M9。
- `summary` 字符串由调用者保证与本轮 removable 历史对应；多轮运行推荐 `summarizer`，它每次获得当前历史。尚未做摘要缓存或增量摘要。
- 保留完整工具事实可能让压缩后仍超限，此时明确失败。后续可在不丢失审计信息的前提下设计文件事实索引。
- 工作区路径检查沿用现有策略，不声称消除检查与读取之间的文件系统竞态；规则来源顺序也不等于模型一定正确遵循自然语言冲突优先级。
- CLI inspect 是诊断命令；默认 fake run CLI 仍不是完整 Coding Tools/SQLite 会话交互入口。M7 的图接线通过 SDK 和集成测试验证。
- 本次归档是文档和验收状态归档，没有创建 Git commit、tag 或推送远端。

## 6. 学习回顾

M7 的核心是把可审计的持久历史与一次模型调用的输入分开。单个函数绿灯无法证明组合正确：摘要前丢消息、摘要后超预算、预算裁剪工具结果，都必须在真实调用链上验证。

M8 从现有 `ChatModel.invoke` 和 `ModelSummarizer` 接入真实 provider，继续处理超时、重试、异步取消；M7 的诊断和失败边界为其提供测试基线。

理解检查：

1. 为什么摘要失败时可以保存本轮失败状态，却不能覆盖旧 checkpoint 的消息？
2. 为什么工具结果只有 1 字节，也不能脱离对应的调用请求单独留在上下文？
3. 为什么某条摘要更短，最终上下文仍可能超出预算？
