## A. 先看整体系统

M0-M2 已经建立了源码映射、Python 项目、带类型的消息状态、模型依赖和单次执行图。M3 负责补齐缺失的动作循环；M4 随后会把无害的假工具替换为受工作区约束的编码工具。

```text
[已完成 M0-M2]                     [当前 M3]                         [后续]
用户 -> 状态 -> 模型 -> AIMessage -> 路由 -> 注册表/验证 -> 执行
                                  \-> END       -> ToolMessage -> 模型 -> END
                                                              |
                                                              +-> M4 安全/HITL
```

如果没有 M3，`AIMessage` 可以包含工具请求，但图会立即结束。模型表达了一个意图，应用却既没有执行动作，也没有返回结果。

贯穿本里程碑的示例是 `add(left=2, right=3)`。预期对话记录如下：

```text
HumanMessage("计算 2 + 3")
AIMessage(tool_calls=[{name: "add", args: {left: 2, right: 3}, id: "call-1"}])
ToolMessage(content="5", tool_call_id="call-1")
AIMessage("结果是 5。")
```

M3 包含注册表、Pydantic 参数验证、稳定的错误工具消息、一个工具节点、条件路由、工具批次最大数量、假工具和确定性测试。它不包含文件系统/进程访问、权限审批、token 流式输出、持久化、重试以及真实供应商。

## B. 当前垂直切片

### Pi 调用链及其设计意图

在 `packages/agent/src/agent-loop.ts` 中，`runLoop()` 接收助手响应、提取工具调用、执行一个批次、把每个结果追加到当前上下文，并在仍有工作时开始下一轮模型调用。关键的内部调用链如下：

```text
runLoop
  -> 检查助手的工具调用
  -> prepareToolCall
       -> 按名称查找工具
       -> 准备/验证参数
       -> 可选的前置钩子
  -> executeToolCallsSequential / executeToolCallsParallel
       -> executePreparedToolCall
       -> 将异常转换为错误结果
  -> createToolResultMessage
       -> 保留工具调用 ID 和工具名称
  -> 将结果追加到上下文
  -> 下一轮模型调用
```

Pi 默认支持并行执行，但会有意按照助手消息中的原始顺序发出需要持久化的工具结果消息。它还会把未知工具、无效参数、被阻止的调用、执行异常和被截断的调用转换为模型可观察的结果，而不是静默丢弃。

### Python/LangGraph 重写

| 问题 | Pi 设计 | M3 选择 | 原因 |
|---|---|---|---|
| 定位一个动作 | 按名称搜索 `AgentContext.tools` | `RunContext` 中的 `ToolRegistry` | 注册表是运行时能力，不是持久状态 |
| 验证不可信的模型参数 | TypeBox 验证 | Pydantic v2 模型 | 明确的 Python 边界和稳定的验证测试 |
| 执行一次调用 | `AgentTool.execute()` | 带类型的 `ToolDefinition.invoke()` | 将模式/处理器与图编排分离 |
| 报告成功/失败 | `ToolResultMessage` | LangChain `ToolMessage` | 标准的、模型可见的工具结果协议 |
| 关联结果 | 保留 `toolCall.id` | 完整保留 `tool_call_id` | 供应商要求每个结果与其请求匹配 |
| 继续或停止 | 命令式 `hasMoreToolCalls` 循环 | 条件边加 `tools -> model` 边 | 使控制流和终止条件可见 |
| 限制失控行为 | 应用的停止策略 | `tool_rounds` 加运行时最大值 | 在无限循环之前返回稳定的终止状态 |
| 多个调用 | 并行或串行模式 | M3 中按来源顺序串行执行 | 确定性的教学基线；并发语义保持显式 |

M3 使用的模型由脚本驱动，并被视为已经能够感知工具。将 JSON Schema 绑定到真实供应商模型属于供应商适配器里程碑；它不会被隐藏在图状态中。

### 状态与失败路径

```text
模型返回无工具调用
  -> status=completed -> END

模型返回工具调用，且仍有剩余轮次
  -> status=awaiting_tools -> tools
  -> 按来源顺序为每次调用生成一条 ToolMessage
  -> tool_rounds += 1 -> model

未知工具 / 无效参数 / 处理器异常
  -> ToolMessage(status="error", 使用相同的调用 ID)
  -> 模型看到失败，并可以修正其请求

达到最大轮数后，模型又请求一个批次
  -> tool_limit 节点发出错误 ToolMessage
  -> status=failed -> END
```

LangGraph 负责应用归约器、调度节点、连接边以及执行循环。应用代码仍负责注册表语义、模式验证、错误规范化、顺序、轮次策略，以及区分安全的假工具与有副作用的生产工具。

## 学习者练习

脚手架创建完成后，只实现 `src/pi_agent/tools/registry.py` 中的 `ToolRegistry.execute_call()`。

输入：一个包含 `name`、`args` 和 `id` 的 LangChain `ToolCall`。

输出：恰好一条 `ToolMessage`，且它的 `tool_call_id` 与输入 ID 相同。

必需行为：

1. 在不修改注册表的情况下查找指定名称的工具。
2. 未知工具：返回错误码为 `unknown_tool` 的 `ToolMessage`。
3. 已注册工具：执行前通过其 Pydantic 模式验证 `args`。
4. 验证失败：不要调用处理器；返回错误码 `invalid_arguments`。
5. 处理器异常：返回错误码 `tool_execution_error`，且不包含堆栈跟踪。
6. 成功：返回处理器生成的字符串结果，并设置 `status="success"`。
7. 保持错误 JSON 的确定性，并在所有路径上保留调用 ID/名称。

工具节点会针对助手的每个工具调用执行一次此函数，并把得到的消息作为状态增量返回。随后，`add_messages` 会把它们插入对话记录，再由固定的 `tools -> model` 边开始下一轮。

## C. 回到整体

### 学习者实现评审

学习者在 `ToolRegistry.execute_call()` 中正确实现了四类必需结果：

- 执行前先查询注册表；
- 未知工具转换为 `unknown_tool` 消息；
- Pydantic 验证失败转换为 `invalid_arguments` 消息，且不会调用处理器；
- 处理器异常转换为不含堆栈跟踪的 `tool_execution_error` 消息；
- 成功调用会保留工具名称和调用关联信息，并返回模型可见的内容。

提交的目标测试结果为 `8 passed`，目标 Ruff 命令也已通过。随后评审发现了两个原有测试未能区分的契约：

1. 处理器自身也可能抛出 Pydantic `ValidationError`。由于验证和执行最初共用同一个 `try` 边界，该处理器失败会被错误归类为模型参数错误。现在，`ToolArgumentError` 只包装模式验证失败，使所有处理器异常都进入执行错误路径。
2. `ToolMessage.id` 为归约器/追踪标识消息本身，而 `tool_call_id` 将结果与助手请求关联起来。学习者提出的确定性 ID 思路得到保留，但消息 ID 现在使用带命名空间的 `tool-result:{call_id}`，而不是复用原始调用 ID。

验证失败现在会返回一条稳定消息以及经过清理的 Pydantic 错误详情，其中省略了输入值、版本 URL 和上下文。图级测试证明，所有三类可恢复的工具错误都会在下一次模型调用前追加到消息中。

### M3 完成后的同一场景

在 M3 之前，`2 + 3` 请求会在助手表达工具调用后停止。完成 M3 后，完整状态演进如下：

```text
HumanMessage("计算 2 + 3")
  -> model_node
  -> AIMessage(tool_call add, id="call-1")
  -> route_after_tool_model 发现 awaiting_tools 且仍有可用轮次
  -> tool_node
  -> ToolRegistry.find("add")
  -> AddArguments.model_validate({left: 2, right: 3})
  -> RecordingAddHandler 返回 "5"
  -> ToolMessage(
       id="tool-result:call-1",
       tool_call_id="call-1",
       status="success",
       content="5"
     )
  -> add_messages 追加结果
  -> 固定的 tools -> model 边
  -> model_node 看到工具结果并返回 "结果是 5。"
  -> route_after_tool_model -> END
```

可恢复的工具失败遵循同一个循环：工具节点返回错误 `ToolMessage`，模型得到修正或解释的机会。显式工具轮次限制则不同：它会路由到 `tool_limit_node`，创建相关联的“未执行”结果，将图状态设为 `failed`，然后结束。

### 必须掌握的知识

1. 工具是由模型可见的身份/模式和应用负责的执行逻辑共同组成的协议边界，而不只是一个 Python 函数。
2. 模型生成的参数是不可信的，必须在产生副作用之前进行验证。
3. 验证失败和执行失败的原因不同，需要各自独立的异常边界。
4. `ToolMessage.tool_call_id` 将结果与一条 `AIMessage.tool_calls` 记录关联；`ToolMessage.id` 是消息自身的身份，供状态/追踪机制使用。
5. 可恢复的工具错误应进入对话记录，让模型能够作出反应；图级终止失败只为耗尽轮次限制等策略保留。
6. 注册表和最大轮次是运行时依赖/策略；消息、已执行轮次数、状态和错误则是持久图状态。
7. 每个图循环都需要显式的语义退出条件；框架递归限制只能作为最后一道防线。
8. M3 按照助手消息中的原始顺序串行执行多个调用。并行执行需要显式定义完成顺序、持久化顺序、取消和事件契约。

### 用户验收——2026-09-11

- 学习者正确区分了可恢复的工具失败与图级轮次限制终止策略：未知工具或暂时失败的工具会返回给模型，使其可以修正计划；耗尽预算则会阻止一个持续失败的无限循环。

- 学习者确认 `max_tool_rounds` 是图级的**批次门槛**，而不是每个工具的重试计数器。一旦已执行工具批次数达到限制，下一个待处理批次将被整体跳过；`tool_limit_node` 为每个请求的调用发出一条相关联的错误结果，将运行标记为 `failed`，然后结束图。
